### A — and a sixth issue found while fixing it

The root cause was my own v0.5 repair. The original bug was the fifty-move test
running *before* checkmate detection; the fix guarded it with `not in_check`,
which conflates **"in check"** with **"checkmated"**. Being in check with legal
moves does not defeat a claimable draw.

Fixing it properly meant reading what the referee actually does, and that
exposed a further gap nobody had reported. The referee ends games with
`board.outcome(claim_draw=True)`, which claims via `can_claim_fifty_moves()` —
and that is already true at a halfmove clock of **99**, not 100, because the
claim may be made for the move about to be played:

```
clock 98: can_claim=False  outcome=None
clock 99: can_claim=True   outcome=FIFTY_MOVES
clock 100: can_claim=True  outcome=FIFTY_MOVES
```

A `>= 100` threshold therefore scores as winning a position the referee has
already drawn. The threshold is now 99, and the claim itself is delegated to
`board.can_claim_fifty_moves()` rather than reimplemented, because getting the
zeroing-move logic subtly wrong is precisely the failure being repaired.

## The single terminal policy

`rules_outcome()` and `no_legal_move_score()` are now used identically by
`_negamax` and `_quiescence`. The two disagreeing is how this went wrong twice.
Ordering, which is the whole substance:

1. **Checkmate outranks every draw.** A mate on the hundredth halfmove is a win.
2. **A claimable fifty-move draw applies even in check**, provided it is not
   mate.
3. **Terminal status precedes every static exit** — the quiescence depth cap,
   the ply ceiling, stand-pat, and SEE or delta pruning.

Everything expensive is gated behind `clock >= 99` or the cap itself, both rare,
which is why the repair is nearly free (below).

## Other items

**C — position validation** now applies to *whatever set is selected*: the
built-in corpus, a custom `--start-fen`, or any future external corpus. A
position is rejected if python-chess rejects it, if the game is already over
before a move, or if the side not to move is in check. The arena exits non-zero
and names the reason; it never silently skips.

**D — provenance** is no longer a hand-maintained list. `cs_search._flag()`
registers every variable it reads into `DECLARED_FLAGS`, `cs_time` declares
`CS_INCREMENT_MS`, and the arena derives `KNOWN_CS_VARS` from both. A test fails
if the engine ever reads a variable the arena would not record.
`CLAUDESHARK_DEBUG` is now registered too, which also makes
`CLAUDESHARK_DEBUG=0` mean off rather than on.

**E — statistics.** The naive interval used the *observed* between-game
variance, which is exactly zero when every game ends the same way. It is now a
Wilson score interval, derived from the binomial rather than the observed
spread, so an all-wins sample yields a finite lower bound that widens as the
sample shrinks. Two honest labels were added: `saturated` when the Elo transform
is at its clamp and the number is a floor rather than a measurement, and
`boot_degenerate` when every cluster scored identically so the bootstrap cannot
estimate spread at all.

**Item 9 — delta pruning.** The risk is real on paper: delta pruning runs before
the push, so it cannot know a capture gives check and is not covered by the SEE
check exemption. No concrete failure could be constructed. Running the whole
search with delta pruning effectively disabled changed the chosen move in
**0 of 42** corpus positions, and in the tactical suite only one position's
*score* moved (1102 vs 1115) with the same move played. **Documented, behaviour
unchanged**, per the brief.

**Item 10 — TT threshold.** The threshold is untouched. But the audit of the
comment found a real gap rather than a stale sentence: the **root store ignored
the halfmove guard** the interior nodes obey, leaving open the exact
contamination path the guard exists to close. Fixed, with a test.

## Regression match

Not an Elo experiment. Its only purpose is to catch a catastrophic playing
regression from the repairs.

```
set CS_SEE_KEEP_CHECKS=0    (planted, to prove stripping and provenance)
uv run python -m tools.arena --agent champions/v0_5_1_correctness ^
    --opponent champions/v0_5_correctness --games 96 --base-ms 20000 ^
    --increment-ms 200 --ply-cap 300 --workers 5 --set-env CS_INCREMENT_MS=200 ^
    --jsonl benchmarks/current/2026-09-02-v0.5.1-regression.jsonl
```

```
champions/v0_5_1_correctness vs champions/v0_5_correctness over 96 games
+26 =47 -23, score 51.6%
elo +11
  Wilson score 95% CI        -58 .. +80
  paired bootstrap 95% CI    -36 .. +55   (24 position clusters)
terminations: checkmate 49, threefold_repetition 41, insufficient_material 6
```

| | |
|---|---|
| games | 96, corpus v2 (`5e05e90376be086e`), 300-ply cap |
| W/D/L | 26 / 47 / 23 |
| score | 51.6% |
| Elo | +11 |
| Wilson CI | −58 .. +80 |
| paired bootstrap CI | −36 .. +55 |
| crashes / flags / illegal | 0 / 0 / 0 |
| environment | `CS_INCREMENT_MS=200` in force, `CS_SEE_KEEP_CHECKS` stripped |

**No regression.** Slightly positive, well inside noise, which is the expected
result for repairs that leave node counts identical.

Note the provenance line: `CS_SEE_KEEP_CHECKS` was deliberately exported into
the parent before launching. It was stripped and recorded. Under v0.5 that same
export would have silently changed both engines while the record read
`effective: {}` — the finding this session fixed, demonstrated rather than
asserted.

Also worth noting: the bootstrap interval here is *narrower* than the Wilson
one, the opposite of the v0.5 match. That is not a contradiction. Wilson
describes uncertainty about the score of a binomial with maximal variance at
p≈0.5; the bootstrap describes how much the result actually varied between
position clusters, and in this match the clusters agreed with each other more
than a binomial would predict. Both are reported precisely because neither is
the whole story.
