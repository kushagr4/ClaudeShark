# v0.3 arena record

Date: 2026-09-02. Machine: 12-core x86-64 Windows laptop, 5 concurrent games.
Opponent: `champions/v0_2` throughout.

All runs used the same conditions unless stated:

```
CS_INCREMENT_MS=200 uv run python -m tools.arena --agent champions/v0_3 \
    --opponent champions/v0_2 --games N --base-ms 20000 --increment-ms 200 \
    --ply-cap 200 --workers 5
```

`CS_INCREMENT_MS` tells both engines the arena's real increment. Without it v0.3
would credit the competition's 500 ms against a clock that only pays 200 ms.
v0.2 ignores the variable and infers the increment instead, which is the
behaviour being replaced.

## Run 1 — 120 games, intermediate v0.3

Snapshot under test: safe LMR, aspiration windows, packed evaluator, rewritten
time management **including a stability heuristic**. Did not yet include the
fifty-move/checkmate fix or the root-table-poisoning fix.

```
+31 =53 -36, score 47.9%
elo -14  (95% CI -61 .. +32)
terminations: checkmate 65, threefold_repetition 51, adjudication 2,
              insufficient_material 2
```

No crashes, no flags, no illegal moves.

## Run 2 — 24 games, v0.3 after removing the stability heuristic

Small by design: this was a validation run looking for crashes and flags, not a
strength measurement. Its interval is ±115 Elo and it settles nothing on its own.

```
+5 =9 -10, score 39.6%
elo -73  (95% CI -197 .. +34)
terminations: checkmate 15, threefold_repetition 9
```

Baseline smoke test the same day: v0.3 vs `baselines/numba`, 8 games, +8 =0 -0.

## Pooling runs 1 and 2

Different code in each, so this is indicative rather than rigorous:

```
+36 =62 -46 over 144 games, score 46.5%
elo -24  (95% CI -68 .. +18)
```

Two runs both below 50% is weaker evidence than one big run, but it is enough to
stop treating the first result as obviously noise, and it is what prompted
looking again for a regression that fixed-depth benchmarks structurally cannot
see.

## The regression that search benchmarks could not see

Aspiration windows were validated at fixed depth, where they are a clear win
(−2.4% to −2.8% nodes, same moves). Fixed-depth runs never run out of time, and
that is exactly what hid the problem.

v0.2 committed a root move that had been fully searched and improved alpha even
when the iteration was later aborted — a real gain, because it banks an
improvement found just before the clock ran out. The first aspiration
implementation refused every partial result from a narrow-window iteration, on
the reasoning that a move beating a *narrow* alpha has not been shown to be best
overall. That reasoning is right about fail-low iterations and wrong about
everything else, and since aspiration applies from depth 4 upward, it removed
the partial-commit behaviour from essentially every real iteration under a
clock.

Fixed by gating on the original alpha instead: a move is committed when its
score genuinely exceeded the window floor, which is always true for a full
window and true for the meaningful cases under aspiration.

**The general lesson: a change validated only at fixed depth has not been
validated for time-limited play.** Anything touching the iterative-deepening
loop, the abort path or move commitment needs an arena or a clock simulation,
because the deterministic instruments cannot reach it.

## Run 3 — 120 games, v0.3 with the partial-commit fix

Same conditions as run 1, so the two are directly comparable.

```
+38 =52 -30, score 53.3%
elo +23  (95% CI -23 .. +71)
terminations: checkmate 65, threefold_repetition 47, insufficient_material 5,
              adjudication 3
```

No crashes, no flags, no illegal moves.

## What the three runs do and do not establish

| run | code | score | Elo | 95% CI |
|---|---|---|---|---|
| 1 (120 games) | pre-fix, stability heuristic | 47.9% | −14 | −61 .. +32 |
| 2 (24 games) | stability heuristic removed | 39.6% | −73 | −197 .. +34 |
| 3 (120 games) | partial-commit fix | **53.3%** | **+23** | −23 .. +71 |

Runs 1 and 3 are directly comparable: identical conditions, identical opponent,
120 games each, differing only in the fix. The point estimate moved 5.4
percentage points, from −14 to +23 Elo.

**Being honest about the statistics:** none of these results is individually
significant — every interval spans zero. The difference between run 1 and run 3
is not significant either (z ≈ 1.1, p ≈ 0.26). 120 games cannot resolve a change
of this size; roughly 400–800 would be needed.

So the case for v0.3 does not rest on the arena alone. It rests on:

* a **proven bug fix** — v0.2 scored a forced mate as a draw whenever the
  fifty-move counter was exhausted, with a reproducible before/after;
* a **provably behaviour-neutral** evaluator speedup: +34% evaluation
  throughput at an *identical* depth-6 node count, so the speed carries no
  strength risk by construction;
* an **identified and fixed regression** in the abort path, which is the most
  likely explanation for the earlier negative results;
* an arena that is now positive rather than negative under identical conditions.

**Outstanding:** a 400+ game run at 20 s + 0.2 s to tighten the interval. Until
that exists, v0.3 is promoted as "very likely better, not proven".

## Run 4 — 400 games, the settled result

Candidate `champions/v0_3` at commit `eec119b`; opponent `champions/v0_2`. Same
conditions as runs 1 and 3. Position selection is deterministic: every FEN in
`tools/positions.BALANCED_OPENINGS` is played twice, once with each engine as
white, cycling through the 24-position suite. No engine code was modified during
the run — the arena plays frozen snapshot directories, so working-tree edits
cannot reach it.

```
CS_INCREMENT_MS=200 uv run python -m tools.arena --agent champions/v0_3 \
    --opponent champions/v0_2 --games 400 --base-ms 20000 --increment-ms 200 \
    --ply-cap 200 --workers 5
```

```
+144 =147 -109, score 54.4%
elo +30  (95% CI +3 .. +58)
terminations: checkmate 247, threefold_repetition 126, insufficient_material 19,
              adjudication 6, fifty_moves 1, stalemate 1
```

| | |
|---|---|
| games | 400 |
| W/D/L | 144 / 147 / 109 |
| score | 54.4% |
| Elo | **+30, 95% CI +3 .. +58** |
| crashes | 0 |
| flags | 0 |
| illegal moves | 0 |
| adjudications | 6 of 400 (1.5%) reached the 200-ply cap |
| decisive games | 247 by checkmate (61.8%) |
| time control | 20 s + 0.2 s, ply cap 200, 5 concurrent |

**The interval excludes zero.** This is the first statistically significant
strength result in the project: v0.3 is stronger than v0.2, not merely
plausibly stronger. It also retrospectively vindicates the partial-commit fix —
runs 1 and 3 differed only in that change and moved the point estimate from −14
to +23, and the larger run lands at +30 with the fix in place.

Worth noting what it took: 120 games could not distinguish −14 from +23. The
same comparison at 400 games resolves to +30 ± 28. Anyone reading the earlier
runs as evidence either way was reading noise.
