# v0.4 (SEE) vs v0.3 — arena

Date: 2026-09-02. Candidate `champions/v0_4` (commit `a12e340`), opponent
`champions/v0_3` (commit `eec119b`). Machine idle apart from the arena.

```
CS_INCREMENT_MS=200 uv run python -m tools.arena --agent champions/v0_4 \
    --opponent champions/v0_3 --games 240 --base-ms 20000 --increment-ms 200 \
    --ply-cap 200 --workers 5
```

240 games is 5 complete passes of the 24-position suite with colours reversed,
so every position is played equally often as white and as black.

```
+68 =105 -67, score 50.2%
elo +1  (95% CI -32 .. +35)
terminations: checkmate 130, threefold_repetition 86, insufficient_material 17,
              adjudication 5, fifty_moves 1, stalemate 1
```

| | |
|---|---|
| games | 240 |
| W/D/L | 68 / 105 / 67 |
| score | 50.2% |
| Elo | **+1, 95% CI −32 .. +35** |
| crashes / flags / illegal moves | 0 / 0 / 0 |
| adjudications | 5 of 240 (2.1%) |

## This is the interesting result

Every deterministic instrument said SEE was a clear win:

| measurement | result |
|---|---|
| nodes at fixed depth 6 | −14.9% |
| wall clock at fixed depth 6 | −16.8% |
| depth at a 900 ms budget | +0.41 ply |
| depth at a 4500 ms budget | +0.34 ply |
| centipawn loss vs reference | 1.5 → 1.9 cp, zero blunders |
| tactical suite | 16/16, unchanged |

The arena says **+1**.

For contrast, v0.3 over v0.2 was a comparable depth gain and measured +30 Elo
(95% CI +3 .. +58) over 400 games. So this is not a case of "the effect was
always going to be too small to see".

## What to conclude, and what not to

**Not proven either way.** The interval runs −32 to +35, so 240 games cannot
exclude a +30 gain any more than it can exclude a small loss. What it does rule
out is the change being *large*, which the deterministic numbers had implied.

The most likely explanation is that the extra depth is not worth as much as
depth usually is, because of *where* it comes from. SEE buys its nodes by
refusing to look at losing captures. Those subtrees are cheap to skip and mostly
irrelevant — which is why the node count falls so much — but the plies bought
with the savings are spent on the same quiet positions the engine already
understood. A ply bought by searching faster is not always worth the same as a
ply bought by pruning better.

This is worth stating plainly because it undermines a habit the project had been
building: treating "+0.4 ply at a realistic budget" as a proxy for strength. It
was a good proxy for the v0.3 changes and a poor one here, and nothing in the
deterministic measurements distinguished the two cases in advance.

## Decision

**Kept, but not claimed as a strength gain.** The reasoning:

* it is not a regression — 50.2% with no crashes, flags or illegal moves;
* it is a genuine efficiency: strictly less work for the same depth, which is a
  proven property rather than an inferred one;
* it is a prerequisite for further pruning work (futility pruning and quiescence
  improvements both want an exchange evaluator).

But the honest headline is that **SEE bought no measurable Elo**, and the
repository says so rather than quoting the node-count table and moving on.

Reverting is a one-line change if the position is later judged wrong: set
`CS_SEE_QS` and `CS_SEE_ORDER` to default `False` in `cs_search.py`.

**Outstanding:** a 400+ game run to narrow the interval, and — more useful — an
experiment that tests the underlying hypothesis directly, by comparing depth
bought through pruning against depth bought through raw speed.
