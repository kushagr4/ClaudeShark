## 1. Which of PVS / null-move / LMR actually pays

**Fixed depth 6, 24 balanced positions.** Deterministic: node counts reproduce
exactly run to run, so this is a comparison of the engines rather than of the
machine. Fewer nodes at equal depth is better.

```
uv run python -m tools.attribute --depth 6 --lmr-safe
```

| variant | nodes | vs baseline | tactics |
|---|---|---|---|
| baseline (v0.1 search) | 5,870,410 | — | 13/13 |
| PVS only | 5,471,327 | −6.8% | 13/13 |
| null-move only | 5,846,694 | **−0.4%** | 13/13 |
| LMR only | 2,195,691 | −62.6% | 13/13 |
| PVS + null-move | 3,478,706 | −40.7% | 13/13 |
| PVS + LMR | 2,142,042 | −63.5% | 13/13 |
| null-move + LMR | 2,196,132 | −62.6% | 13/13 |
| all three (v0.2) | 1,990,684 | −66.1% | 13/13 |
| v0.2 + safe LMR | 2,001,875 | −65.9% | 13/13 |

**Null-move pruning is worth nothing on its own (−0.4%) and 34 points in
combination with PVS.** The cause is structural, not statistical: null-move is
gated on `beta - alpha == 1`, and without PVS there are no null-window nodes for
it to fire at. It is dead code without PVS.

Marginal contribution, removing one feature from the full combination:

| removed | nodes | cost of removing |
|---|---|---|
| PVS | 2,196,132 | +9.4% |
| null-move | 2,142,042 | +7.1% |
| LMR | 3,478,706 | +42.8% |

**Verdict: keep all three.** This overturns the previous session's suggestion
that PVS might be droppable for saving "only 1.3% of nodes" — that figure was
measured with null-move already present, which hid the fact that PVS is what
makes null-move work at all.

## 2. Does LMR cost move quality?

```
uv run python -m tools.movequality --depth 6 --ref-depth 6 --suite balanced
uv run python -m tools.movequality --depth 7 --ref-depth 7 --suite sharp
```

Centipawn loss against a PVS-only reference (PVS is score-exact; null-move and
LMR are the approximations being tested).

| suite | variant | agree | avg loss | worst | >100cp |
|---|---|---|---|---|---|
| balanced, d6 | v0.2 | 23/24 | 0.3 | 7 | 0 |
| balanced, d6 | v0.2 + safe LMR | 23/24 | 0.3 | 7 | 0 |
| balanced, d6 | no LMR | 24/24 | 0.0 | 0 | 0 |
| sharp, d7 | v0.2 | 12/16 | 0.7 | 8 | 0 |
| sharp, d7 | v0.2 + safe LMR | 12/16 | 0.7 | 8 | 0 |
| sharp, d7 | no LMR | 15/16 | 0.0 | 0 | 0 |

LMR costs well under a centipawn on average and never blundered. **Safe LMR
chose an identical move in all 40 positions**, so it is not an Elo change; it
was enabled on robustness grounds at a measured cost of 0.6% nodes. See the
comment on `LMR_SAFE` in `cs_search.py`.

## 3. Evaluator optimisation

Packed middlegame/endgame scores into one integer per square and unrolled the
twelve bitboard scans.

```
uv run python -m tools.profile_eval
uv run python -m tools.bench --depth 6
```

| metric | before | after | change |
|---|---|---|---|
| evaluations/second | 196,378 | 264,053 | **+34%** |
| microseconds/evaluation | 5.09 | 3.79 | −26% |
| search nodes/second (depth 6) | 64,833 | 68,808 | **+6.1%** |
| depth-6 node count | 2,001,875 | 2,001,875 | **identical** |

The identical node count is the point: the optimisation is provably
behaviour-neutral, so the speed is free of strength risk. `tests/test_eval.py`
asserts the fast evaluator agrees with a transparent reference implementation on
every suite position plus 400 positions reached by random legal play.

## 4. Aspiration windows

```
CS_ASPIRATION=0/1 uv run python -m tools.bench --depth 7
CS_ASPIRATION=0/1 uv run python -m tools.bench --depth 8
```

| depth | off | on | change |
|---|---|---|---|
| 7 | 3,462,176 nodes / 54.2 s | 3,364,903 / 51.8 s | −2.8% nodes, −4.4% time |
| 8 | 8,422,010 nodes / 125.1 s | 8,223,751 / 121.0 s | −2.4% nodes, −3.3% time |

23 of 24 root moves unchanged at depth 8; the single move that changed matched
the unpruned reference's preference. Small, consistent, contained in one
function. **Kept.**
