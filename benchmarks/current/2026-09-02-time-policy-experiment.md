# Time-policy experiment — can unused clock become strength?

Date: 2026-09-02. Base: **v0.3** (`eec119b`), the proven champion.

## Why v0.3 and not v0.4

v0.3 is the only version with a statistically significant strength result
(+30 Elo, 95% CI +3 .. +58, over 400 games against v0.2). v0.4's SEE change
measured +1 Elo (CI −32 .. +35) and is explicitly experimental. Branching the
time experiment from v0.4 would mean one unproven change riding on another, and
any result would be unattributable. All candidates here are v0.3 plus a single
constant.

## The candidates

Generated by `tools/make_time_variants.py`, which copies the base champion,
substitutes one constant, and then **refuses to write the variant unless the
only textual difference across every `.py` file is that one line**. Verified
after generation: only `cs_time.py` differs, by exactly one line.

| policy | `START_FRACTION` | meaning |
|---|---|---|
| A — `champions/v0_3` | 0.45 | current champion, unchanged |
| B — `champions/v0_3_sf60` | 0.60 | moderately more aggressive |
| C — `champions/v0_3_sf75` | 0.75 | aggressive |

Search, evaluation, transposition table, ordering and quiescence are byte-identical
across all three.

## Where the unused clock was going

Diagnosed from the 234-ply CSV of the previous session's real-clock run before
changing anything:

```
soft/clock ratio  mean 0.0479
hard/soft  ratio  mean 3.000
spent/soft ratio  mean 0.679  median 0.655
spent/hard ratio  mean 0.226
plies exceeding soft: 27/234 (12%)
```

This isolates the cause. `hard/soft` is exactly 3.000 on every ply, so the
`usable * MAX_SHARE_OF_CLOCK` cap never binds — the hard deadline is always
`soft * 3`. `spent/hard` is 0.226, so the search is nowhere near being aborted.
The reserve and the IPC overhead together are 240 ms against a soft budget of
several seconds, so they are not the cause either.

What remains is `should_start_iteration()`, which refuses to begin another
iterative-deepening pass once `START_FRACTION = 0.45` of the soft budget has
elapsed. Because an iteration costs roughly 2–4x the one before, the last
iteration that *is* started typically finishes around 68% of soft — matching the
measured 0.679 — and only 12% of plies run past soft at all.

**The unused clock is one constant, and it is not a safety margin.** The safety
margins (reserve, overhead, hard deadline, one-third cap) were all found to be
inactive.

The end-of-game reserve is a second-order consequence of the same thing. With
`moves_to_go = 26` and 68% utilisation, spending per move is
`0.679 * (usable/26 + 375)`, against 500 ms credited. Solving for equilibrium
gives a clock that asymptotes near 9.4 s rather than depleting, which is why
games finished with ~20% left.

## Real 120 s + 0.5 s behaviour

`uv run python -m tools.gamesim --games 2 --engine champions/<policy>`

| | A (0.45) | B (0.60) | C (0.75) |
|---|---|---|---|
| plies | 156 | 209 | 319 |
| mean ms/move | 2434 | 2294 | 1950 |
| median ms/move | 2317 | 2196 | 1499 |
| max ms/move | 8570 | 7964 | 8053 |
| **soft budget used** | **73.7%** | **96.0%** | **118.6%** |
| mean depth | 7.11 | 8.18 | 8.03 |
| first half vs second | 2883 / 1984 | 2568 / 2022 | 2840 / 1066 |
| **lowest clock** | **25,574 ms (21.3%)** | **5,751 ms (4.8%)** | **1,297 ms (1.1%)** |
| hard-deadline overruns | 0 | 0 | 0 |
| panic-mode plies | 0 | 0 | 0 |

Game lengths differ because the policies play differently, which confounds the
per-move averages and the lowest-clock figure — a longer game depletes more. The
soft-budget utilisation is the clean comparison, and it moves exactly as
intended: 73.7% → 96.0% → 118.6%.

**Policy C is rejected on safety.** Finishing a game with 1,297 ms is one
scheduling hiccup away from a flag, and a mean utilisation above 100% means the
soft deadline has stopped functioning as a deadline at all. It is kept as a
frozen snapshot for the record, not as a candidate.

**Policy B is the candidate.** It converts nearly all of the allocated budget
into search without ever overrunning a hard deadline or entering panic mode.

## Safety ladder

`uv run python -m tools.clockladder --engine champions/<policy>`

Every policy returns a **legal move at every clock from 1 ms to 120 s**, across
six positions including in-check, one-legal-move and endgame cases. Policies A
and B both PASS.

Two honest notes about this ladder:

* At a **1 ms clock** every engine takes ~2 ms, because constructing the board
  and generating legal moves costs that much before any policy is consulted.
  The tool originally failed all three here; the criterion was wrong, not the
  engines. Below `CLOCK_FLOOR_MS = 50` only legality is required.
* At a **250 ms clock** the arithmetic goes degenerate: `usable = 250 − 40 − 200
  = 10 ms`, giving a hard deadline of 3.3 ms, which is far below the fixed cost
  of even a depth-1 search. The engine spends ~21 ms — 8.5% of the real clock,
  so there is no flag risk — but it necessarily exceeds its own computed hard
  deadline. `PANIC_MS = 120` is too low: the panic path should engage whenever
  `usable` falls below the cost of a single iteration, not at a fixed 120 ms.
  **Not fixed in this session**, because it is a second change and would break
  the single-variable discipline. Recorded as the next candidate after this
  experiment concludes.

## Does more time produce better moves?

`uv run python -m tools.timequality --a champions/v0_3 --b champions/v0_3_sf60
--clock 20000 --ref-depth 6 --suite both`

```
A = champions\v0_3        mean depth 5.90
B = champions\v0_3_sf60   mean depth 6.26   (+0.36 ply)

agreed on 39/42 positions
of the 3 disagreements, by the reference:
  B better  0
  B worse   0
  level     3
  net       -4 cp
```

**The extra time changes the chosen move in 3 of 42 positions**, and on those
three a less-selective reference rates the two moves as level.

Two limitations, stated because they cut against reading too much into this: a
depth-6 reference adjudicating depth-6 moves is a weak oracle, close to
circular; and this is a single cold-transposition-table search rather than a
move inside a game, so it likely understates the in-game effect where the table
is warm and differences compound.

Even so, the agreement rate is oracle-independent and is the striking number. It
is the same shape as the SEE result: a measurable increase in search that mostly
re-confirms the move the engine already had.
